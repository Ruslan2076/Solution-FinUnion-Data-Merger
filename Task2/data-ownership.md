# Правила владения данными

## 1. Роли и их разграничение

| Роль | Кто это | За что отвечает | Чего не делает |
|---|---|---|---|
| Data Owner | Руководитель бизнес-подразделения из структуры объединённой компании | Смысл данных, правила изменения, утверждение правил качества и порогов, разрешение конфликтов владения | Не занимается технической реализацией проверок |
| Data Steward | Назначенный сотрудник подразделения-владельца или Data Office | Ежедневный контроль качества, разбор карантина, ведение карточки сущности в каталоге, инициирование исправлений | Не меняет бизнес-правила без владельца |
| Producer | Система или команда, создающая данные | Соблюдение контракта публикации, версионирование схемы, уведомление потребителей об изменениях | Не решает, кто имеет право читать данные |
| Consumer | Система или подразделение, использующее данные | Соблюдение контракта чтения, регистрация подписки в каталоге | Не изменяет данные в обход мастер-системы |

Правило, замыкающее роли: метрика качества без порога и без конкретного человека, разбирающего карантин, не работает. Поэтому в таблице правил ниже у каждой сущности указаны и порог, и подразделение, отвечающее за разбор.

## 3. Правила изменения и правила качества

Пороги заданы для промежуточного состояния и пересматриваются владельцем по итогам первого квартала работы объединённого ландшафта.

| ID | Сущность | Правила изменения | Обязательные проверки качества и пороги |
|---|---|---|---|
| E-01 | Клиент | Идентифицирующие атрибуты меняются только через MDM. Контактные атрибуты меняет CRM своего банка и публикует изменение в шину. Слияние двух записей выполняется только после подтверждения правила сопоставления; неоднозначные пары уходят в карантин и не сливаются автоматически | Уникальность: доля неразрешённых дублей не выше 1% клиентской базы, работа останавливается при 3%. Полнота идентифицирующих атрибутов не ниже 98%. Консистентность GCID во всех системах-потребителях — 100%. Своевременность распространения GCID — не более 5 минут |
| E-02 | Участие в договоре | Роли создаются только вместе с договором в системе-мастере. Изменение доли участия требует документа-основания | Полнота ролей: у каждого договора минимум одна сторона — 100%. Полнота созаёмщиков в структурированном виде не ниже 95% для новых договоров |
| E-03 | Договор | Создание и закрытие — только в мастер-системе своего банка. Статус меняется по утверждённой статусной модели; прямые правки в базе запрещены | Внутренняя консистентность дат: дата закрытия не раньше даты открытия — 100%. Полнота ссылки на продуктовый код — не ниже 99% для новых договоров. Кросс-системная сверка количества договоров между АБС и DWH — расхождение не более 0,1% |
| E-04 | Продукт | Новый продукт заводится только в MDM. Сопоставление продуктов двух банков утверждается продуктовым подразделением, а не выполняется автоматически по совпадению названия | Уникальность кодов — 100%. Полнота линии бизнеса — 100%. Консистентность справочника во всех потребителях — расхождение версий не более одних суток |
| E-05 | Тариф | Изменение условий создаёт новую версию тарифа, старая версия не перезаписывается. Дата вывода из обращения обязательна при деактивации | Полнота даты ввода и вывода — 100%. Полнота версии, зафиксированной в договоре — 100% для новых договоров |
| E-06 | Счёт | Открытие и закрытие — только в АБС своего банка. Остаток изменяется исключительно проводками, прямое редактирование остатка запрещено | Точность остатка: сверка АБС и DWH на конец дня, допустимое расхождение — ноль. Полнота обязательных реквизитов — 100%. Своевременность выгрузки остатков — не позднее 2 часов после закрытия операционного дня |
| E-07 | Карта | Выпуск, перевыпуск и блокировка — только в процессинге. Связь перевыпущенной карты с предшественником обязательна к заполнению | Уникальность: каждая карта имеет ссылку на предшественника при перевыпуске — не ниже 98%. Консистентность статуса между процессингом и CRM — 100% после синхронизации. Полный номер карты в общих контурах отсутствует — 100% |
| E-08 | Кредитная сделка | Выдача, изменение графика и признание просрочки — только в кредитной системе. Правила расчёта просрочки фиксируются в единой методике, различия двух банков отражаются как атрибут метода расчёта | Точность задолженности: сверка кредитной системы и АБС на конец периода, расхождение — ноль. Полнота обеспечения — не ниже 95%. Консистентность статуса дефолта с единой методикой — 100% |
| E-09 | Кредитная заявка | Решение по заявке меняет только андеррайтинг. Сохранность среза данных на момент решения — 100% |
| E-10 | Платёж | Распоряжение создаётся только в системе своего банка с обязательным ключом идемпотентности. Повторная отправка с тем же ключом не создаёт новое распоряжение | Уникальность по ключу идемпотентности — 100%. Полнота назначения платежа — не ниже 99%. Своевременность статуса в витрине поддержки — не более 5 минут от изменения статуса |
| E-11 | Операция | Проводка неизменяема. Корректировка выполняется отдельной сторнирующей операцией, а не правкой существующей | Своевременность: лаг между временем события и временем загрузки не более 1 часа для операций текущего дня. Полнота обеих меток времени — 100%. Консистентность кодов операций с единым классификатором — не ниже 99% |
| E-12 | Обращение | Регистрация и закрытие — в CRM своего банка. Категория обращения проставляется по единому классификатору объединённой компании | Полнота предмета обращения — не ниже 90%. Уникальность: доля дублей обращений, поступивших по двум каналам, не выше 2%. Соблюдение SLA — метрика владельца, порог задаёт контактный центр |
| E-13 | Согласие | Выдача и отзыв фиксируются в неизменяемом журнале. Отзыв распространяется во все системы-потребители; локальное игнорирование отзыва недопустимо | Полнота признака согласия — 100% для активных клиентов. Своевременность распространения отзыва — не более 15 минут, работа маркетинговых выгрузок останавливается при превышении. Целостность журнала — 100% |
| E-14 | Отделение | Заведение и закрытие точки — только в MDM. Дата закрытия обязательна | Уникальность кодов после маппинга — 100%. Полнота даты закрытия для неактивных точек — 100%. Консистентность региональной нарезки с единым классификатором — 100% |
| E-15 | Сегмент | Правило отнесения утверждает продуктовое подразделение и регистрирует в MDM. Расчёт выполняется в DWH по расписанию; ручное переназначение сегмента требует обоснования | Полнота: доля клиентов без сегмента не выше 5%. Своевременность пересчёта — не реже одного раза в месяц. Консистентность правила между банками — 100% после утверждения единых правил |

## 4. Разрешение конфликтов владения

Если на сущность претендуют две системы или два подразделения, это означает, что границы владения не определены, а не то, что нужна двусторонняя синхронизация. Порядок разрешения:

1. Проверить, не является ли конфликт атрибутным. В большинстве случаев спор снимается разделением: MDM ведёт паспортные данные и ИНН, CRM — телефон и email.
2. Если конфликт на уровне записей, зафиксировать разделение по группам: каждый банк остаётся мастером своих клиентов и договоров до завершения соответствующей миграционной волны.
3. Если разделение невозможно, решение принимает Data Owner домена, а Data Office фиксирует его в каталоге данных вместе с датой и основанием.
4. Неоднозначно сопоставленные записи изолируются в карантине. Автоматический выбор победителя по времени изменения запрещён: некорректное обновление не вызывает технической ошибки и успешно расходится по всем системам-потребителям.

Для каждого временного механизма переходного периода — маршрутизации в шине, таблиц соответствия, параллельных потоков — заранее фиксируется критерий отключения. Без него временная совместимость становится постоянной частью архитектуры.
