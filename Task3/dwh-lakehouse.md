# DWH на PostgreSQL и Data Lakehouse

## 1. Сравнение для кейса FinUnion + RetailBank

| Критерий | DWH на PostgreSQL | Data Lakehouse |
|---|---|---|
| Где выполняются вычисления | Внутри той же СУБД, где лежат данные; ресурсы ограничены одним сервером | В отдельном кластере запросов; хранение отделено от вычислений и масштабируется независимо |
| Подход к схеме | Schema-on-write: схема витрин зафиксирована заранее, данные подгоняются под неё до записи | Schema-on-read: данные сохраняются как есть, схема накладывается при чтении |
| Пригодность для данных кейса | Договоры, счета, кредитные сделки, агрегаты по операциям — структурированные данные с известной моделью | История карточных операций за несколько лет, события мобильного и веб-каналов, файлы клиринга, архивные выгрузки RetailBank, вложения к обращениям |
| Стоимость хранения истории | Растёт линейно и упирается в дисковую подсистему сервера | Объектное хранилище дешевле на порядок при том же объёме |
| Повторная обработка истории | Требует повторного обращения к системам-источникам, если сырой слой не сохранён | Сырой слой сохраняется всегда, пересчёт идёт из него |
| Режим ИБ | Персональные данные маскируются до записи, в хранилище не оседают в открытом виде | Сырые чувствительные данные физически лежат в хранилище, защита строится на ролевой модели и псевдонимизации при переходе между слоями |
| Воспроизводимость отчёта на прошлую дату | Через историчность в модели данных: версии измерений, снапшоты | Через снимки таблиц: состояние на прошлую дату восстанавливается средствами формата |
| Требования к компетенциям | SQL и привычные инструменты, новых компетенций не требуется | Партиционирование, размеры файлов, обслуживание снимков, эксплуатация SQL-движка |
| Срок до первого результата | Недели | Месяцы |
| Что ломается при небрежной эксплуатации | Витрины расходятся с бухгалтерией, расчёт мешает пользовательским запросам | Хранилище превращается в набор файлов без владельцев, где каждая команда собирает свою версию отчётности |

Существенное различие для этого кейса не в производительности, а в том, какие данные каждый контур способен принять. Задача объединения требует обоих типов: регламентированная отчётность строится на согласованной структурированной модели, а объединённая история операций двух банков и события каналов в такую модель не помещаются.

## 2. Выбранный подход по состояниям

### Промежуточное состояние, 3 месяца

**DWH на PostgreSQL, без Lakehouse.**

Состав: слой загрузки, согласованный слой и витрины по клиентам, счетам, продуктам и операциям. Загрузка оркеструется Airflow, трансформации выполняются SQL внутри хранилища.

Почему так:

- Требование промежуточного состояния — единая управленческая отчётность и минимальный набор витрин для BI. Это профиль классического хранилища.
- Стек знаком обеим командам. Осваивать новую платформу одновременно с переносом критичных данных не следует: при сбое невозможно понять, ошибка в миграционной логике или в новой технологии.
- В первые месяцы в хранилище попадают согласованные данные и агрегаты, а не полная детальная история. Объём удерживается в границах, где реляционная СУБД справляется.

Что сознательно не делается на этом этапе: полная история карточных операций не загружается, события каналов не собираются, архивы RetailBank остаются в исходных выгрузках. Эти данные ждут Lakehouse.

### Финальное состояние, 12 месяцев

**DWH сохраняется для регламентированной отчётности, Lakehouse добавляется для истории и событий.**

| Контур | Что в нём | Кто потребитель |
|---|---|---|
| DWH | Согласованный слой и сертифицированные витрины, регуляторная и управленческая отчётность | Финансовый департамент, регулятор, BI |
| Lakehouse | Полная история операций, события каналов, архивы, обучающие выборки | Риск-менеджмент, антифрод, аналитика, ML |

Связь между контурами односторонняя: подготовленные наборы серебряного слоя Lakehouse загружаются в DWH как источник, обратного потока нет. Это удерживает регламентированную отчётность в одном контуре с фиксированной моделью и не даёт ей зависеть от гибкой схемы.

Пересмотр класса решения для DWH — отдельное решение по результатам профилирования объёмов. Если детальных фактов окажется сотни миллионов строк и ночной расчёт перестанет укладываться в окно, PostgreSQL заменяется на MPP или колоночную СУБД. Архитектурная логика при этом не меняется: приёмка, согласование в общем слое, публикация витрины.

## 3. Роль Apache Iceberg и Trino

Объектное хранилище само по себе таблицами не управляет: оно хранит файлы и ничего не знает о том, какие из них образуют актуальную версию набора данных. Iceberg и Trino закрывают два разных пробела.

**Apache Iceberg — управляемая таблица поверх файлов.** Создаёт логический объект над набором Parquet-файлов и хранит метаданные: состав файлов, актуальную схему, схему партиционирования, текущий снимок и снимки, существовавшие раньше. Каталог метаданных связывает имя таблицы с её текущим снимком.

Что это даёт в кейсе:

- **Атомарность публикации.** Новые данные пишутся в новые файлы, текущая версия таблицы остаётся доступной. Каталог переключает ссылку на новый снимок только после успешной записи. Потребитель видит либо старую, либо новую целостную таблицу, но не промежуточное состояние. Для ночного пересчёта витрин это означает, что аналитик, открывший дашборд во время загрузки, не увидит половину данных.
- **Изоляция и воспроизводимость.** Снимки позволяют восстановить состояние таблицы на прошлую дату. Для объединения двух банков это прямо полезно: при расхождении в отчётности можно сравнить, каким был набор данных до и после применения очередной порции истории RetailBank.
- **Управление схемой.** Схема таблицы — часть метаданных, а не устная договорённость. Добавление поля не требует перезаписи истории.

Отдельная эксплуатационная обязанность: неактуальные снимки нужно периодически архивировать или удалять, иначе объём служебных файлов растёт без пользы.

**Trino — распределённый SQL-движок.** Данные не хранит и объектное хранилище не заменяет. Принимает SQL-запрос, строит план, распределяет обработку между рабочими узлами и возвращает результат.

Как это работает на запросе к золотому слою:

1. Координатор принимает запрос, проверяет существование каталога, схемы, таблицы и полей, а также права пользователя, затем строит логический план.
2. Через коннектор Iceberg получает из каталога метаданных сведения об актуальном снимке: какие файлы входят в текущую версию таблицы, где они лежат, как таблица разделена на партиции, какие диапазоны значений содержит каждый файл.
3. По статистике партиций исключает файлы за ненужные периоды. Запрос по одному месяцу карточных операций не читает историю за пять лет.
4. Логический план превращается в распределённый, данные делятся на части, координатор распределяет их между рабочими узлами.
5. Каждый узел читает назначенные файлы, выбирает только нужные столбцы, применяет фильтр и считает частичный результат.
6. Частичные результаты объединяются, координатор возвращает итог BI-системе или аналитику.

Практическое следствие для архитектуры: вычисления отделены от хранения, поэтому при росте аналитической нагрузки наращивается кластер запросов, а данные не переносятся в отдельную СУБД. Но производительность определяется не только числом узлов: партиционирование, размеры файлов, статистика и структура запроса влияют на неё не меньше.

## 4. Распределение данных между контурами

| Данные | Контур | Почему именно там |
|---|---|---|
| Согласованный слой договоров, счетов, кредитных сделок | DWH | Структурированные данные с известной моделью, основа регламентированной отчётности, требуется воспроизводимость показателя на дату по фиксированной методике |
| Витрины по клиентам, счетам, продуктам и операциям | DWH | Сертифицированные наборы для BI с единым определением показателей и семантическим слоем |
| Регуляторная отчётность | DWH | Строится из согласованного слоя, а не из витрин: витрины оптимизированы под управленческие разрезы и могут не совпадать с методикой регулятора |
| Измерения, построенные на справочниках MDM | DWH | Небольшой объём, частые соединения, требование единой версии справочника во всех витринах |
| Полная история операций двух банков за прошлые годы | Lakehouse | Объём и требование повторной обработки. Хранение в реляционной СУБД дороже, а пересчёт требовал бы обращения к системам-источникам, часть из которых будет выведена из эксплуатации |
| Карточные операции в виде потока событий | Lakehouse, слой bronze | Высокочастотный поток с разнородной структурой от двух процессингов с разными кодами операций |
| События мобильного и веб-каналов | Lakehouse | Полуструктурированные данные, схема меняется вместе с релизами приложений |
| Архивные выгрузки RetailBank | Lakehouse, слой bronze | Разнородные форматы, нужны для повторной обработки и для восстановления происхождения после вывода legacy-систем |
| Обучающие выборки для скоринга и антифрода | Lakehouse, слой gold | Требуется полная история и возможность пересобрать выборку под новую модель без обращения к источникам |
| Сканы договоров, вложения к обращениям | Объектное хранилище | Запись один раз, чтение редко, поиск обеспечивается внешним индексом и метаданными |
| Таблица соответствия псевдонима и GCID | Отдельный контур, ни в DWH, ни в Lakehouse | Если ключ лежит рядом с данными и доступен тем же людям, правовой режим не снижается, а пайплайн получает лишний шаг |
| Полный номер карты и код проверки | Изолированный контур процессинга | Отдельный, более жёсткий режим работы с карточными данными. В общие контуры передаётся маскированный номер и токен |

Граница между контурами проводится не по возрасту данных, а по двум признакам: нужна ли фиксированная методика расчёта и помещается ли структура в заранее заданную схему. История договоров пятилетней давности остаётся в DWH, если участвует в отчётности, а события каналов недельной давности идут в Lakehouse, потому что их схема меняется с каждым релизом приложения.

## 5. Ограничения выбранного подхода

**Два контура — это две копии части данных.** Подготовленные наборы серебряного слоя загружаются в DWH, то есть одни и те же факты существуют в обоих хранилищах. Каждая копия наследует правовой режим оригинала и требует собственных правил хранения и удаления. Риск: расхождение между витриной DWH и золотым набором Lakehouse при разной логике расчёта. Мера: критичные показатели рассчитываются в одном месте, второй контур их потребляет, а не пересчитывает.

**Lakehouse без governance деградирует предсказуемо.** Медальонная архитектура — это не три папки с именами bronze, silver и gold. Для каждого слоя нужны правила публикации, проверки качества, владельцы и права доступа. У FinUnion уже есть частичный Data Lake без единого каталога, lineage и правил качества — то есть образец того, во что превращается озеро без управления. Мера: набор данных без владельца, схемы и правил качества не публикуется.

**Сырые чувствительные данные физически оседают в хранилище.** Это плата за быструю первую загрузку. Мера: псевдонимизация на переходе из бронзового слоя в серебряный, огрубление квазиидентификаторов, проверка на уникальность записей по набору квазиидентификаторов перед публикацией золотого набора.

**Производительность Trino не является константой.** Она зависит от партиционирования, размеров файлов, статистики и структуры запроса. Мелкие файлы, накопленные потоковой загрузкой, деградируют чтение. Мера: регламентное объединение мелких файлов и удаление неактуальных снимков как эксплуатационная задача с владельцем, а не как разовая настройка.

**Компетенции команды — ограничивающий фактор.** Ни у FinUnion, ни у RetailBank нет опыта эксплуатации Lakehouse: у одного банка частичное озеро без управления, у другого нет и этого. Мера: новые компоненты проверяются на ограниченном сценарии до начала миграции критичных данных.

**Выбор PostgreSQL для промежуточного DWH основан на непроверенном допущении об объёме.** Количество клиентов и операций в кейсе не задано. Если профилирование покажет сотни миллионов строк детальных фактов, класс решения нужно менять сразу, а не через год.
