## Ключевые решения

- **Гибрид вместо выбора одного подхода.** DWH для регламентированной отчётности, Lakehouse для истории и событий, элементы Data Mesh поверх обоих. Первые два отвечают на вопрос, где хранить, третий — кто владеет; они не взаимозаменяемы.
- **Полноценный Data Mesh не проектируется, и это обоснованный отказ.** Подход требует зрелых доменных команд, которых в компании в процессе слияния нет. Раздача владения несформированным командам даст двенадцать версий отчётности вместо двух. Берутся продуктовое мышление и федеративное управление — они работают и при централизованной платформе.
- **Промежуточный DWH на PostgreSQL, целевой класс решения — под вопросом объёма.** Объёмы в кейсе не заданы. Если профилирование покажет сотни миллионов строк детальных фактов, класс решения нужно менять сразу, а не через год. Это допущение названо явно в `architecture-options.md`.
- **Регуляторная отчётность строится из согласованного слоя DWH, а не из витрин и не из Lakehouse.** У регулятора требования к методике и воспроизводимости, а не к гибкости схемы.
- **Единый классификатор операций применяется на переходе bronze → silver, а не при загрузке.** Бронзовый слой хранит исходные коды двух процессингов: при обнаружении ошибки в словаре соответствия пересчитывать историю иначе будет не из чего.
- **Гранулярность факта — одна проводка по счёту.** Платежи и остатки в эту таблицу не смешиваются: платёж изменяем и может породить несколько проводок, остаток — состояние, а не событие.
- **Схема «Звезда», риск денормализации закрывается организационно.** Источник всех справочных атрибутов один — MDM. Измерения собираются из него и переиспользуются несколькими витринами.
- **Продукт без подтверждённого потребителя не публикуется.** Набор данных без владельца, контракта и требований к качеству остаётся технической таблицей.
