# Технологическая дорожная карта

## 1. Разграничение с планом миграции

Миграционный план и технологическая дорожная карта описывают разные стороны перехода. План миграции показывает, какое состояние данных достигается на каждом этапе. Дорожная карта показывает, какие платформенные возможности должны появиться, чтобы это состояние стало достижимым.

Правило наполнения: технология не попадает в дорожную карту без связи с результатом. Если для возможности нельзя назвать этап миграции, который без неё не выполняется, эта возможность в карту не включается.

## 2. Дорожная карта возможностей

| Горизонт | Возможности | Зачем нужны | Какой этап миграции без них не выполняется |
|---|---|---|---|
| 0–3 месяца | MDM Customer Hub, PostgreSQL DWH со слоями staging, core и витрин, Airflow, Integration Layer с реестром схем, базовые проверки качества и карантин | Запустить согласованный пилотный аналитический контур и присвоить клиентам корпоративный идентификатор | Этапы 1 и 2: без MDM нет GCID и объединять портфели не с чем; без DWH и Airflow нет пилотной витрины |
| 3–6 месяцев | DataHub с каталогом и lineage, CDC для критичных потоков, Kafka для событийных, витрина качества с порогами, контур управления согласиями | Обеспечить прослеживаемость происхождения, назначить владельцев, снять аналитическую нагрузку с операционных систем, закрыть регуляторный риск по отзывам согласий | Этап 3: без CDC расширение периметра усилит нагрузку на АБС; этап 7: без lineage невозможно вывести legacy, не потеряв происхождение исторических показателей |
| 6–9 месяцев | Объектное хранилище, Apache Iceberg, Trino, медальонные слои с правилами публикации, псевдонимизация на переходе между слоями, графовая БД, поисковый движок | Перенести большие исторические и событийные данные, обеспечить воспроизводимость состояния на дату, закрыть задачи антифрода и дедупликации по неточному совпадению | Этап 4: история карточных операций двух банков не помещается в реляционное хранилище ни по объёму, ни по разнородности схем |
| 9–12 месяцев | Доменные data-продукты с паспортами и контрактами, автоматическая проверка контрактов в конвейере сборки, семантический слой с владельцами показателей, вывод legacy-контура | Передать ответственность за смысл данных владельцам и завершить переход | Этапы 5 и 7: без контрактов и владельцев перенос таблицы в доменную схему не создаёт продукт, а вывод legacy без реестра потребителей блокируется первым же забытым потребителем |

### 2.1. Обоснование по ключевым компонентам

**MDM в первом горизонте, а не позже.** Присвоение корпоративного идентификатора — вход для всех последующих этапов. Отложить его означает выполнять объединение портфелей по фамилии и дате рождения, то есть воспроизвести в новом контуре ту же проблему дублей, ради устранения которой затевается программа.

**CDC во втором горизонте, а не в первом.** В первом горизонте пилот работает на ограниченном срезе, и ежедневной пакетной выгрузки достаточно. CDC становится обязательным на этапе 3, когда в аналитический контур подключается весь операционный периметр двух банков: прямые выгрузки такого объёма конкурируют с транзакциями ядра.

**Iceberg и Trino в третьем горизонте.** Iceberg нужен не потому, что это современный формат, а потому что требуются четыре конкретные вещи: управляемая история больших таблиц, снапшоты для воспроизведения состояния на дату, эволюция схемы без перезаписи истории и SQL-доступ через распределённый движок. Trino отвечает за последнее: отделяет вычисления от хранения, позволяя наращивать кластер запросов, не перенося данные в отдельную СУБД.

**Контур согласий раньше вывода RB CRM.** Отзыв согласия, не дошедший до потребителей, — прямое нарушение требований к обработке персональных данных. Отключать CRM, в которой хранятся согласия, до запуска контура нельзя.

**Data Mesh как изменение модели ответственности, а не как технология.** Доменные команды должны получить владельцев продуктов, контракты, SLA и платформенные шаблоны. Перемещение таблицы в доменную схему само по себе data-продукта не создаёт: без владельца, потребителей, контракта и процесса поддержки получается распределённое хранилище, но не распределённое владение.

## 3. Технологический радар

Дорожная карта отвечает на вопрос «когда нужна возможность». Радар отвечает на другой: «насколько технология готова к использованию в этой компании». Статус зависит от контекста: одна и та же технология может быть в Adopt у компании с сильной экспертизой и в Assess у компании без команды сопровождения.

| Зона | Технологии и подходы | Обоснование для FinUnion + RetailBank |
|---|---|---|
| **Adopt** | PostgreSQL DWH, Airflow, MDM, DataHub, Integration Layer с реестром схем, объектное хранилище для документов и архивов | Команды обоих банков работают с реляционными хранилищами и SQL ежедневно; у FinUnion есть шина, то есть опыт централизованной маршрутизации. Эти компоненты можно ставить в промышленный контур сразу. DataHub попадает сюда не из-за зрелости команды, а из-за отсутствия альтернативы: без каталога вывод legacy-систем нечем подготовить, а порог входа в ведение карточек и lineage низкий |
| **Trial** | Apache Iceberg, Trino, CDC, Kafka, медальонные слои, графовая БД | Нужен пилот на реальном объёме и проверка эксплуатации. У FinUnion есть частичное озеро без каталога и правил качества — это опыт хранения файлов, но не опыт управляемого Lakehouse. У RetailBank нет и этого. Освоение этих компонентов одновременно с переносом критичных данных создаёт риск R-20: при сбое непонятно, ошибка в миграционной логике или в новой технологии. Поэтому каждый из них проходит ограниченный сценарий до включения в миграцию |
| **Assess** | Модель Data Mesh, ClickHouse и другие колоночные СУБД, MPP-платформы, управляемые облачные аналитические платформы, семантический слой как отдельный продукт | Data Mesh требует зрелых доменных команд, которых в сливающейся компании нет: оценивается применимость и готовность организации, а не технология. Колоночные и MPP-решения оцениваются по результатам профилирования объёмов на этапе 0 — если PostgreSQL перестанет укладываться в окно расчёта, они переходят в Trial. Облачные платформы оцениваются после ответа службы ИБ о допустимости размещения обезличенных данных |
| **Hold** | Новые точечные интеграции, прямой доступ BI и аналитических систем к операционным базам, развитие RB DWH, свободная двусторонняя синхронизация мастер-данных, автоматический выбор победителя при конфликте записей, ручные выгрузки в качестве постоянного механизма | Каждый подход увеличивает связанность и стоимость будущей миграции. Новая точечная интеграция добавляет ещё одного потребителя, которого придётся искать при выводе legacy. Прямой доступ к операционным базам нарушает ограничение кейса и уже сегодня создаёт конкуренцию нагрузок. Развитие RB DWH удлиняет список того, что придётся переносить. Синхронизация по правилу «последнее изменение побеждает» теряет корректные изменения молча, без технической ошибки — это самый опасный класс дефектов в программе |

### 3.1. Условия перехода между зонами

| Технология | Текущая зона | Что переводит в следующую зону | Что возвращает назад |
|---|---|---|---|
| Apache Iceberg, Trino | Trial | Успешный ограниченный сценарий на реальном объёме: перенос истории одного продуктового сегмента, воспроизведение состояния на дату, приемлемое время отклика BI | Деградация чтения из-за мелких файлов, которую не удаётся удержать регламентным обслуживанием |
| CDC, Kafka | Trial | Работа на потоках двух банков без потерь сообщений в течение периода наблюдения | Потери сообщений на финансовых данных, где допустимый уровень нулевой |
| Графовая БД | Trial | Подтверждённый сценарий антифрода: обход связей на три-четыре шага за приемлемое время на реальном объёме | Отсутствие компетенций сопровождения после пилота |
| Колоночные и MPP-решения | Assess | Профилирование показало объём, при котором PostgreSQL не укладывается в окно расчёта | — |
| Облачные платформы | Assess | Служба ИБ подтвердила допустимость размещения обезличенных аналитических данных | Ограничение подтверждено — остаются в Assess до пересмотра требований |
| Data Mesh | Assess | Сформированы доменные команды с собственной аналитической компетенцией и работает платформа самообслуживания | — |
| PostgreSQL DWH | Adopt | — | Расчёт витрин не укладывается в окно два периода подряд: класс решения пересматривается, компонент уходит в перестройку |

## 4. Связь дорожной карты с этапами миграции

| Этап миграции | Требуемые возможности | Горизонт появления |
|---|---|---|
| 0. Инвентаризация | Инструменты профилирования, доступ к журналам запросов | Доступно сейчас |
| 1. Мастер-данные | MDM, Integration Layer с реестром схем, витрина качества и карантин | 0–3 месяца |
| 2. Пилотный DWH | PostgreSQL DWH, Airflow, контур автоматической сверки | 0–3 месяца |
| 3. Расширение периметра | CDC, Kafka, единый классификатор операций | 3–6 месяцев |
| 4. Lakehouse | Объектное хранилище, Iceberg, Trino, псевдонимизация между слоями | 6–9 месяцев |
| 5. Data-продукты | DataHub, контракты с автоматической проверкой, семантический слой | 3–6 месяцев для каталога, 9–12 для контрактов |
| 6. Миграция ядра RetailBank | Контур согласий, маршрутизация между мастерами, механизмы обратной синхронизации | 3–6 месяцев |
| 7. Вывод legacy | Полный lineage в каталоге, реестр потребителей, мониторинг обращений к legacy | 9–12 месяцев |

Строка «5. Data-продукты» разнесена по двум горизонтам намеренно: каталог нужен раньше, чем контракты, потому что без него нечем вести реестр потребителей для этапа 7, а автоматическая проверка контрактов имеет смысл только когда продукты уже публикуются и у них появились зависимости друг от друга.
