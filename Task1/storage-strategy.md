# Типы хранилищ и распределение данных

## 1. Порядок принятия решения

Сначала фиксируется режим доступа — это ограничение, которое нельзя обойти оптимизацией. Внутри оставшихся вариантов выбирается хранилище по профилю нагрузки. После выбора проверяется, не породило ли решение новых копий данных: реплик, резервных копий, журналов, дампов для тестовых стендов. Каждая копия наследует правовой режим оригинала.

## 2. Контуры хранения

| ID | Тип хранилища | Что размещается | Профиль нагрузки | Ограничения, которые принимаем |
|---|---|---|---|---|
| ST-01 | OLTP, реляционная СУБД | E-03 договор, E-02 участие, E-06 счёт, E-07 карта (без полных карточных данных), E-08 кредитная сделка, E-09 заявка, E-10 платёж, E-11 операция за оперативный период | Точечные чтения и записи, короткие транзакции, требование ACID, отклик в десятки миллисекунд | Изменение схемы требует релиза, горизонтальное масштабирование записи ограничено. На профиле операционного банковского учёта это приемлемо: схема стабильна, а целостность важнее гибкости |
| ST-02 | MDM | Золотая запись E-01 клиент, справочники E-04 продукт, E-05 тариф, E-14 отделение, E-15 сегмент, реестр соответствия локальных идентификаторов FinUnion и RetailBank | Умеренный объём записи, дедупликация и matching, чтение по ключу и по атрибутам, публикация изменений подписчикам | MDM не обслуживает высокочастотное чтение в каналах — под это ставится реплика. Внедрение требует согласованных правил владения, иначе получится ещё одна база с дублями |
| ST-03 | DWH, колоночная или MPP | Регламентированная отчётность регулятору, управленческая отчётность, витрины по клиентам, счетам, продуктам и операциям | Тяжёлые сканы и агрегации, регламентный расчёт, задержка в часы приемлема | Точечные обновления дороги, транзакционность ограничена. Для регламентированной отчётности это не мешает: данные загружаются пакетно и не правятся по одной записи |
| ST-04 | Data Lakehouse (объектное хранилище, табличный формат, распределённый SQL-движок) | Полная история E-11 операций, события каналов, исторические выгрузки RetailBank, обучающие выборки для скоринга и антифрода, слои bronze — silver — gold | Большие объёмы, разнородные схемы, повторная обработка истории, отделение хранения от вычислений | Отклик выше, чем у DWH, требуется дисциплина публикации по слоям. Без правил доступа и владельцев по каждому слою превращается в неуправляемое озеро — то, что уже описано как проблема FinUnion Data Lake |
| ST-05 | Объектное хранилище | Сканы документов и вложений к E-12 обращениям, подписанные договоры, архивные выгрузки двух банков, резервные наборы данных | Запись один раз, чтение редко, большой объём, дешёвое долговременное хранение | Нет запросов по содержимому: поиск обеспечивается внешним индексом и метаданными. Служит также физическим слоем для ST-04 |
| ST-06 | Графовая БД | Связи между клиентами и контрагентами: созаёмщики и поручители (E-02), общие платёжные реквизиты и получатели (E-10), общие устройства и адреса, бенефициары ЮЛ | Обходы связей на три-четыре шага, отклик меньше секунды, умеренная частота запросов | Узкая ниша и дефицит компетенций, слабая производительность на массовых агрегациях. Обоснована: задача антифрода и выявления связанных заёмщиков после слияния формулируется как «кто с кем связан», и ни реляционная, ни колоночная СУБД не дают обход на четыре шага за секунду. Узлы графа идентифицируются токенами, исходные значения в граф не попадают, восстановление личности по подозрительному кластеру — отдельная процедура в другом контуре с журналированием |
| ST-07 | Поисковый движок | Полнотекстовый индекс по E-12 обращениям, нечёткий поиск по E-01 клиенту для оператора контактного центра и для разбора кандидатов на слияние записей | Полнотекстовые и нечёткие запросы, высокая частота чтения, ранжирование результатов | Индекс не является мастером и допускает задержку синхронизации; при расхождении источником истины остаётся ST-01 или ST-02. Обоснован: дедупликация клиентов двух банков требует поиска по неточному совпадению ФИО, адреса и контактов, что SQL-запросом к АБС не решается; контактный центр ищет по тексту обращений, которых в объединённой компании кратно больше |
| ST-08 | Key-value | Сессии дистанционных каналов, кеш баланса и остатков для мобильного приложения, ключи идемпотентности платежей, признаки для онлайн-скоринга | Доступ строго по известному ключу, десятки тысяч запросов в секунду, отклик в единицы миллисекунд | Запрос только по ключу, долговечность настраиваемая. Размещаются только данные, бесполезные в отрыве от сессии; ключом служит токен сессии, а не идентификатор клиента. Срок жизни кеша согласуется с бизнесом: для статуса платежа устаревшее значение приводит к повторной оплате |

## 4. Почему одна СУБД не закрывает задачу

Разделение продиктовано ограничением кейса: аналитика не должна создавать нагрузку на операционные системы. Сегодня оба банка нарушают это ограничение — batch-выгрузки идут напрямую из АБС и процессинга, а исторические данные RetailBank лежат в DWH вперемешку с отчётными витринами. Попытка обслужить операционный учёт, регламентированную отчётность, поиск по обращениям и графовый антифрод из одного хранилища даёт предсказуемый результат: регламентный расчёт блокирует операционные транзакции, поиск по тексту деградирует, а обход связей на несколько шагов не выполняется вовсе.

Обратная крайность — присвоить всем сущностям высшую категорию и закрыть доступ — тоже не работает: аналитика не исчезает, а уходит в неконтролируемые выгрузки на рабочие станции. Поэтому вместо запрета применяется псевдонимизация с отдельным контуром ключа.
